# Contexto completo del proyecto CamouMacro

## 1. Información general

Proyecto: CamouMacro
Ruta local: C:\Users\paulo\CamouMacro
Fecha de contexto: 2026-08-16
Sistema operativo: Windows (aunque se ejecuta también en Kali/Linux en algunos entornos)

Este proyecto automatiza flujos web con CamouFox + Playwright, orientado especialmente a la plataforma Allfeellove. Está pensado para crear perfiles, acceder a búsquedas de usuarios, filtrar por edad/país/sexo, localizar perfiles objetivo, abrir perfiles, enviar likes/winks, escribir mensajes personalizados y enviar stickers. También incluye una interfaz de terminal para seleccionar diferentes algoritmos y una gestión de navegador con perfiles persistentes y proxy/Tor opcional.

El proyecto usa:
- Python 3.12 / 3.14 según el entorno
- Camoufox
- Playwright
- Tor (opcional para salida de red)
- per-file modular architecture

## 3. Objetivo funcional del proyecto

La app intenta automatizar la creación de una cuenta y luego el flujo de interacción con la plataforma Allfeellove, con estos pasos:
1. abrir la web de Allfeellove,
2. aceptar cookies si aparecen,
3. completar registro con nombre, fecha de nacimiento, género, tipo de búsqueda,
4. registrar email/password,
5. avanzar por onboarding inicial,
6. reclamar bonus/tokens,
7. abrir cuenta de búsqueda,
8. aplicar filtros (edad, país, género, etc.),
9. recorrer páginas de resultados,
10. localizar perfiles objetivos por nombre/edad,
11. entrar a ese perfil,
12. enviar like/wink,
13. activar chat si hace falta,
14. mandar mensajes,
15. enviar stickers,
16. iterar según sea necesario.


## 4. Estado de implementación actual

### 4.1 Driver principal
Archivo: core/camoufox_handler.py

Características clave:
- clase CamoufoxHandler
- inicialización de Camoufox con `Camoufox(**kwargs)`
- `geoip` habilitado si Tor está disponible
- soporte para proxy SOCKS local de Tor (`socks5://127.0.0.1:9050`)
- `rotate_connection()` para reiniciar salida de red si Cloudflare bloquea la página
- `is_tor_available()` para comprobar si 127.0.0.1:9050 está escuchando
- `initialize()` prepara perfil, verifica Tor, entra al navegador y crea page
- `navigate(url)` intenta navegar con varios fallos y reintento
- `verify_ip()` intenta validar el uso de Tor en check.torproject.org

La clase está diseñada para que el algoritmo consuma `driver.page` y `driver.navigate()` y se mueva sobre la página sin tener que manejar detalles de navegador.

### 4.2 Automatización de páginas
Archivo: modules/browser_automation.py

Incluye utilidades como:
- `safe_click`
- `human_type`
- `select_multiselect_option`
- `check_checkbox`
- `scroll_to_selector`
- `wait_for_visible`
- `element_exists`
- `navigate`

Su propósito es encapsular acciones repetitivas y hacerlas más humanas, con tiempos aleatorios y espera por visibilidad.

### 4.3 Algoritmo Allfeellove
Archivo: modules/allfeellove_auto.py

Este módulo tiene la lógica principal. En varias iteraciones se ha ido reescribiendo porque el sitio real tiene cambios estructurales en la UI, especialmente en el listado de resultados y en el botón de paginación.

Funciones clave:
- `run()`: entrada del algoritmo
- `_run_algorithm()`: flujo principal
- `_get_visible_profile_names()`: extrae nombres visibles de la página
- `_collect_profile_cards()`: busca tarjetas reales de perfiles
- `_extract_name_and_age_from_card()`: extrae nombre y edad desde la carta de perfil
- `_scan_profile_batch_fast()`: compara target_profiles con cards visibles
- `_find_profile_card_by_name()`: localiza un perfil por nombre/edad
- `_go_to_next_profile_page()`: avanza la paginación
- `_interact_with_found_profile()`: abre perfil, da like/wink/mensaje/stickers
- `_ensure_chat_mode()`: activa chat si la vista de perfil está en Mail


## 5. Problemas históricos realmente observados

### 5.1 Error de GeoIP / Camoufox extra
Mensaje que apareció en Docker:
- "Please install the geoip extra to use this feature: pip install camoufox[geoip]"

Causa: El proyecto tenía `requirements.txt` con `camoufox` sin extra para GeoIP y el driver usaba `geoip: tor_available`.

Corrección aplicada:
- Dockerfile actualizado
- requirements.txt actualizado
- install_dependencies.py actualizado

Se dejó como:
- camoufox[geoip]

Verificación: se ejecutó un `docker build -t camoumacro-test .` con éxito y la imagen compiló correctamente.

### 5.2 Error de Tor timeout / ipecho.net
Mensaje:
- Failed to get IP address: SOCKSHTTPSConnectionPool(host='ipecho.net', port=443): Max retries exceeded ... ConnectTimeoutError

Causa:
- Camoufox intentaba usar Tor y consultaba ipecho.net para verificar IP
- Pero Tor no estaba activo o no escuchaba en 127.0.0.1:9050
- O estaba corriendo en un contenedor donde 127.0.0.1 no apuntaba al host real

Importante:
- No es un error del algoritmo mismo; es de infraestructura de red/Tor
- En Kali/Linux el servicio Tor debe estar arrancado y escuchando en 9050

Comandos útiles:
- sudo systemctl status tor
- sudo systemctl enable --now tor
- sudo service tor start
- ss -lntup | grep 9050
- sudo tail -f /var/log/tor/notices.log

### 5.3 Falla de DOM / selectors incorrectos
Se detectaron varios errores por lógica de extracción basada en selectores genéricos:
- `'str' object has no attribute '_impl_obj'`
- error por usar `filter(has='...')` con string, cuando Playwright espera un Locator
- reconocimiento erróneo de despliegues de menú y encabezados como si fueran perfiles reales
- confusión con textos como "Profiles", "All", "Filters", "People", "Messages", etc.

Esto indica que la estrategia de escaneo estaba demasiado basada en suposiciones, no en la estructura real del DOM.

### 5.4 Estancamiento en la primera página
El log actual muestra claramente:

[allfeellove_auto] Filtros Terminados...
[allfeellove_auto] Página 1. Nombres visibles: ['Newsfeed\nMessages', 'Mail\nSearch', 'People\nCredits', 'Account\n\nActivate', 'Click', 'Didn', 'Resend Mail', 'Change Your', 'Email Address', 'Profiles\n\nAll', 'Online\n\nFollowing', 'Filters']

Esto significa que el algoritmo no estaba detectando tarjetas adecuadas del listado de usuarios. Estaba leyendo la navegación del sitio y no la lista real de perfiles.

## 7. Estrategia correcta para el escaneo de perfiles

La estrategia correcta no debe buscar texto libre ni encabezados ni menús de navegación. Debe ser específica y basada en la forma del DOM que se ha observado.

### Regla de oro
Buscar solo los elementos que cumplen estas condiciones:
- `div.search-profile-card` o `[data-test-id*="file:search-item"]`
- que tengan al menos un nombre visible dentro del contenedor
- y una edad visible dentro de la misma tarjeta

### Filtros recomendados para descartar elementos no perfil
Cualquier elemento que contenga una de estas cadenas debe excluirse:
- "Profiles"
- "All"
- "Filters"
- "Newsfeed"
- "Messages"
- "Mail"
- "Search"
- "Account"
- "Activate"
- "Resend Mail"
- "Click"
- "Didn"
- "Following"
- etc.

### Estrategia recomendada
1. localiza todos los elementos `div.search-profile-card` o `[data-test-id*="file:search-item"]`
2. iterar sobre ellos, no sobre body completo
3. para cada tarjeta, buscar nombre con:
   - `p.ui-typography.color.name`
   - `p[data-test-id*="person-name"]`
4. buscar edad con:
   - `p[data-test-id*="person-display-age"]`
5. normalizar texto (`Zhade` -> `zhade`, `, 36` -> 36)
6. comparar con `target_profiles` por nombre + edad
7. si coincide, abrir la vista del perfil y interactuar
8. si no, intentar click en el botón Next exacto
9. repetir la búsqueda en la siguiente página

Esta estrategia evita caer en menús, cabeceras, botones de navegación y otros elementos no relevantes.


## 8. Recomendaciones para un agente nuevo

### Qué no hacer
- No volver a buscar sobre `body` o sobre selectores genéricos con `h3, h4, h5`
- No usar `filter(has='...')` con string en Playwright
- No buscar por "Profile" o "Profiles" como identificador de un usuario
- No iterar sobre todos los textos del DOM sin filtrar por tarjeta real
- No depender demasiado de `get_by_text` para perfiles porque el sitio tiene many UI texts

### Qué sí hacer
- Trabajar desde la clase `div.search-profile-card`
- Validar que se ve parte del nombre y parte de la edad en la misma tarjeta
- Mantener un `target_map` con nombres normalizados
- Priorizar `data-test-id` y `class` discriminantes
- Usar `force=True` solo en clics finales y no en todas las interacciones

### Qué verificar antes de avanzar a otra página
- que la lista `div.search-profile-card` esté visible
- que el botón Next realmente exista y sea visible
- que el contenido de la página actual haya cambiado tras el click

## 10. Resumen ejecutivo

El proyecto ya pasó por varios ciclos de depuración, y el problema principal actual no es tanto las dependencias sino la lógica de scraping. El navegador está arrancando, la app llega a la página de búsqueda, pero el algoritmo intenta detectar perfiles usando selectores demasiado generales. El sitio real usa cartas `search-profile-card` con nombre y edad claramente marcados, y la estrategia debe enfocarse en esas tarjetas reales en lugar de los elementos de navegación del dashboard.

El siguiente agente debería partir desde esta base:
- ignorar menús y textos de navegación,
- buscar solo `div.search-profile-card` / `[data-test-id*="file:search-item"]`,
- extraer nombre y edad de ese card,
- navegar con el botón Next exacto de Allfeellove,
- y comparar targets por nombre + edad con normalización robusta.

## 13. Recomendación final para continuidad

El siguiente agente debería empezar por reescribir el bloque de búsqueda de perfiles con esta arquitectura:

- `_collect_profile_cards()` -> devuelve solo `div.search-profile-card` y `search-item`
- `_extract_name_and_age_from_card()` -> extrae únicamente datos del perfil real
- `_scan_profile_batch_fast()` -> compara el target usando un dict normalizado
- `_go_to_next_profile_page()` -> usa el selector exacto del botón Next
- `_scan_profiles_until_found()` -> itera páginas sólo si hay cards reales, si no, finaliza o reintenta con una estrategia de espera/re-render

Con ese enfoque, la lógica deja de confundirse con la UI del menú y se centra en la capa real de dados del sitio.
